## 1. 이 문서가 다루는 것

PRD **F5 뉴스-DART 공시 연계 및 AI 분석**(SQ4 "뉴스에 나온 변화가 실제 공시와 사업 활동으로 확인되는가")의 두 가지 작업을 정의한다.

| # | 작업 | 화면 (F5) | 스토리 · 검수 기준 | LLM 사용 |
|---|---|---|---|---|
| M1 | 뉴스-공시 매칭 | 이슈 ↔ 관련 공시 연결 목록 | US-15 · AC-15 | 없음 (규칙) |
| M2 | 공시 질의응답(RAG) | 공시 Q&A 창 | US-16, US-17 · AC-16, AC-17 | 임베딩 + 답변 생성 |

기업별 기사량 vs 공시 시점 차트(US-14 · AC-14)는 `v_company_daily` 를 그대로 그리면 되므로 이 문서에서 다루지 않는다.

두 작업의 역할은 다르다. **M1은 "어떤 공시를 볼지" 골라 주고, M2는 "그 공시에 뭐라고 적혀 있는지" 답한다.** 감성 분류(T1)가 뉴스의 영향 방향을 붙인다면, M1·M2는 그 뉴스에 **확인된 근거**를 붙인다 (PRD N6).

## 3. M1 뉴스-공시 매칭 규칙

### 3-1. 매칭 조건

세 조건을 모두 만족하면 연결한다.

| 조건 | 규칙 | 근거 |
|---|---|---|
| 같은 기업 | `news_companies.match_field IN ('title', 'body')` 인 기업과 `disclosures.corp_code` 가 같다 | PRD 4절: `query` 는 관련도가 낮아 기업 단위 분석에서 제외 |
| 시점 창 | 3-2절 | |
| 주제 대응 | 뉴스의 CDMO 키워드와 공시의 `event_class` 가 3-3절 표에서 대응한다 | 같은 기업·같은 시기라도 무관한 공시를 걸러낸다 |

중복 기사(`dup_of IS NOT NULL`)는 제외한다. 5개사가 언급되지 않은 기사(해외 CDMO, 정책 기사 대부분)는 매칭 대상이 아니다. 이 한계는 8절에 적는다.

### 3-2. 시점 창 (가설)

| 창 | 범위 (기사 발행일 기준 공시 접수일) | 용도 |
|---|---|---|
| 직접 | −7일 ~ +7일 | 같은 사건을 다룬 기사와 공시. 수주·증설 공시는 계약 당일~익일에 접수되고 기사도 그 전후에 나온다고 가정 |
| 후속 | +8일 ~ +90일 | "이 이슈 이후 실제 사업 활동이 있었나" 확인. 화면에서 직접 매칭과 구분해 표시 |

두 범위 모두 **검증 전 가설**이다. DB가 준비되면 수주 공시 98건에 대해 "접수일 ±N일 안에 같은 기업의 수주 키워드 기사가 있는 비율"을 N = 1, 3, 7, 14로 계산해 직접 창을 확정하고, 결과를 이 절에 기록한다.

### 3-3. CDMO 키워드 ↔ event_class 대응

| 뉴스 CDMO 키워드 | 직접 창에서 연결할 event_class | 후속 창에서 연결할 event_class |
|---|---|---|
| CDMO 수주 | 수주 | 수주, 실적 |
| CDMO 생산능력 | 증설, 자금조달 | 증설, 자금조달, 수주 |
| CDMO 경쟁 구도 | M&A·구조개편, 수주 | M&A·구조개편, 수주, 증설 |
| CDMO 모달리티 | 임상·허가·기술계약, 증설 | 임상·허가·기술계약, 증설, 수주 |
| CDMO 규제·정책 | (없음) | 수주, 증설, M&A·구조개편 |
| CDMO 지정학 | (없음) | 수주, 증설, M&A·구조개편 |

- 규제·정책과 지정학 기사는 공시와 **같은 사건**을 다루지 않으므로 직접 매칭을 하지 않고, 후속 창으로 "정책 이후 사업 활동"만 본다. 이는 선후 관계일 뿐 **인과를 뜻하지 않는다**는 문구를 화면에 둔다.
- `리스크` 공시는 키워드와 무관하게 같은 기업·직접 창이면 연결한다 (11건, 모두 삼성바이오로직스).
- 한 기사에 CDMO 키워드가 여러 개면(`news_cdmo_keywords`) 각 키워드의 대응을 합친다.
- `cdmo_kw_basis='query'` 기사는 연결하되 신뢰도 낮음으로 표시한다 (PRD 4절).

### 3-4. 정정 공시

`is_amended=1` 인 공시(154건, 수주 98건 중 49건)는 **제외하지 않고 "정정" 표시와 함께 연결**한다. 계약 금액·기간이 바뀐 최신 내용이 정정 공시에 있기 때문이다. 원공시와 정정 공시를 잇는 키는 현재 스키마에 없다(미확인). 같은 계약의 묶음이 필요해지면 `report_nm` 과 원문 속 계약 상대방으로 묶는 방법을 따로 정한다.

### 3-5. 정렬과 산출물

한 기사에 연결된 공시는 직접 창 → 후속 창, 그 안에서 `event_weight` 높은 순 → 날짜가 가까운 순으로 정렬한다.

결과는 미리 계산해 파일로 저장한다 (PRD N2). `news_id` 는 빌드마다 바뀔 수 있으므로 뉴스 키는 `url` 을 쓴다.

`data/processed/news_disclosure_links.csv` (제안)

| 컬럼 | 설명 |
|---|---|
| `url` | 뉴스 키 |
| `corp_code` | 기업 |
| `rcept_no` | 공시 키 |
| `window` | `direct` / `follow` |
| `day_gap` | 공시 접수일 − 기사 발행일 (일) |
| `news_keyword` | 연결 근거가 된 CDMO 키워드 |
| `event_class`, `event_weight`, `is_amended` | 공시 속성 |
| `kw_low_confidence` | `cdmo_kw_basis='query'` 이면 1 |

### 3-6. 이슈 단위로 올리기

화면 요구는 "**이슈** ↔ 관련 공시"인데, 이슈 추출(T2)은 아직 설계 전이다 ([AI_CLASSIFICATION](AI_CLASSIFICATION.md) 1절). 그래서 M1은 **기사 단위**로 먼저 만들고, 이슈 ID가 생기면 이슈에 속한 기사들의 연결을 합쳐 공시별 연결 기사 수로 정렬한다. T2가 늦어지면 CDMO 키워드 × 기업 × 월을 임시 이슈 단위로 쓴다.

## 4. M2 공시 RAG 구성

### 4-1. 흐름

```
[사전 생성]  disclosure_documents.text → 청킹 → 임베딩 → chromadb (chroma_db/)
[질의 시점]  질문 → 범위 확인 → 검색(필터 + 유사도) → 답변 생성 → 인용 검증 → 답변 또는 거절
```

색인(청킹·임베딩)은 미리 만들어 저장하고(PRD N2), 대시보드는 저장된 색인을 읽기만 한다. 질문은 사용자가 입력하므로 **질의 시점의 임베딩 1회와 LLM 호출 1회는 불가피**하다. PRD N1의 "대시보드에서 LLM 분류를 실시간으로 수행하지 않는다"와 충돌하지 않는다고 해석했으나 팀 확인이 필요하다 (7절).

### 4-2. 청킹 기준

| 항목 | 기준 (가설) | 이유 |
|---|---|---|
| 대상 | `seq = 1` 본문. `seq ≥ 2` 첨부(감사보고서 등)는 1차에서 제외 | 파일 891개 중 첨부는 약 27개로 추정(891 − 864, 미확인). 첨부는 길고 질문과 거리가 멀다 |
| 분할기 | `langchain-text-splitters` 의 `RecursiveCharacterTextSplitter`, 구분자 `\n\n` → `\n` → 공백 | 원문은 태그를 제거한 텍스트이고 표는 행마다 줄바꿈되어 있어, 줄 단위로 자르면 표의 한 행이 중간에 끊기지 않는다 |
| 크기 | 1,000자, 겹침 150자 | 수주 공시의 계약 표(상대방·금액·기간)가 한 청크에 들어오는 크기로 가정 |
| 짧은 공시 | 1,000자 이하는 통째로 한 청크 | |
| 머리말 | 각 청크 앞에 `[기업명 | 보고서명 | 접수일]` 한 줄을 붙여 임베딩 | 청크만 떼어 놓으면 어느 회사의 어떤 공시인지 사라진다 |

표 처리: 표는 ` | ` 로 칸이 구분된 줄로 들어 있다. 표가 길어 청크가 나뉘면 뒤 청크에는 표 머리(열 이름)가 없다. 1차에서는 그대로 두고, 평가에서 표 관련 질문이 틀리면 표 머리 줄을 뒤 청크에 반복해 붙인다.

크기와 겹침은 평가 질문(6절)으로 500자·1,000자·1,500자를 비교해 확정한다.

### 4-3. 임베딩 모델 (결정 필요)

팀의 LLM 호출은 현재 OpenAI API(`OPENAI_API_KEY`, `analysis/label_sentiment.py`)를 쓴다. 키를 하나로 유지하려면 임베딩도 OpenAI 임베딩 모델을 쓰는 것이 단순하다. 한국어 공시와 한국어 질문이 대상이므로 다국어를 지원하는 모델이어야 한다. 모델 이름과 비용은 실행 시점에 확인해 이 절과 [AI_EVALUATION](AI_EVALUATION.md)에 기록한다.

`requirements.txt` 에는 `langchain-anthropic` 만 있고 OpenAI용 LangChain 패키지가 없다. OpenAI로 정하면 `langchain-openai` 를 추가해야 한다.

| 컬렉션 | `disclosures` |
| 문서 ID | `{rcept_no}-{seq}-{chunk_idx}` |

메타데이터:

| 키 | 출처 | 용도 |
|---|---|---|
| `rcept_no` | `disclosures` | 근거 공시 식별, 인용 검증 |
| `seq`, `chunk_idx` | `disclosure_documents` | 청크 위치 |
| `corp_code`, `corp_name` | `companies` | 기업 필터 (F7) |
| `rcept_date` | `disclosures` — 정수 `YYYYMMDD` 로 저장 | 기간 필터 (범위 비교가 가능하도록 정수) |

| `event_class`, `is_amended` | `disclosures` | 유형 필터, 정정 표시 |
| `url` | `disclosures` | 근거 표시: DART 링크 |

### 4-5. 검색

1. **범위 확인** — 질문에 5개사가 아닌 기업명이 있으면 검색하지 않고 거절한다 (AC-17 "범위 밖 기업"). 기업명 판별은 `collect/config.py` 의 `COMPANY_PATTERNS` 를 재사용한다.
2. **필터** — 대시보드 공통 필터(F7)의 기업·기간과 질문에서 찾은 기업명을 chromadb `where` 조건으로 건다.
3. **유사도 검색** — 후보 20개를 가져와, 같은 공시(`rcept_no`)에서는 상위 2개 청크까지만 남기고 최종 5개를 답변에 넘긴다 (모두 가설).
4. **정정 우선** — 같은 보고서명의 원공시와 정정 공시가 함께 걸리면 접수일이 늦은 것을 앞에 둔다.

### 4-6. 답변 체인

LangChain으로 `검색기 → 프롬프트 → LLM → 출력 파서` 를 잇는다. 답변 LLM은 감성 분류와 같은 모델을 쓰는 것을 제안한다 (결정 필요).

프롬프트 규칙:

- 주어진 공시 발췌에 **적힌 내용만으로** 답한다. 발췌에 없는 수치·날짜·상대방을 추측하지 않는다.
- 답의 각 문장에 근거 공시의 `rcept_no` 를 붙인다.
- 발췌로 답할 수 없으면 `refused: true` 로 답한다.
- 투자 판단·전망을 묻는 질문에는 공시에 적힌 사실만 전하고 판단은 하지 않는다.

출력 형식 (JSON):

```json
{
  "refused": false,
  "answer": "답변 본문",
  "citations": [
    {"rcept_no": "…", "quote": "근거가 된 원문 구절"}
  ],
  "refusal_reason": null
}
```

`report_nm`·`rcept_date`·`url` 은 LLM이 쓰게 하지 않고 **코드가 `rcept_no` 로 메타데이터에서 채운다.** LLM이 링크나 날짜를 지어내는 것을 막기 위해서다.

### 4-7. 거절 기준

아래 중 하나라도 해당하면 답변 대신 거절 문구를 보여준다 (PRD F5 필수 조건, AC-17).

| 단계 | 거절 조건 | 예 |
|---|---|---|
| 검색 전 | 5개사가 아닌 기업에 대한 질문 | "론자의 2025년 수주는?" |
| 검색 후 | 최상위 청크의 유사도가 임계값 미만 | 공시와 무관한 질문 |
| 생성 후 | LLM이 `refused: true` 로 답함 | 존재하지 않는 계약을 묻는 질문 |
| 검증 | `citations` 가 비었거나, 인용한 `rcept_no` 가 검색된 청크에 없음 | LLM이 근거를 지어낸 경우 |
| 검증 | `quote` 가 해당 청크 원문에 없음 (공백 정규화 후 비교) | 인용 구절 환각 |

유사도 임계값은 임베딩 모델에 따라 달라지므로 **미정**이다. 평가 질문(6절)의 답 있는 질문과 거절 질문의 점수 분포를 보고 정한다.

거절 문구(안): "수집한 5개사 공시(2023-10-19 ~ 2026-10-19)에서 근거를 찾지 못해 답변하지 않습니다."

### 4-8. 근거 표시 형식

답변 아래에 인용한 공시를 표로 보여준다 (AC-16: 공시명·제출일·DART 링크).

| 기업 | 공시명 | 제출일 | 근거 구절 | 링크 |
|---|---|---|---|---|
| `corp_name` | `report_nm` (정정이면 "정정" 표시) | `rcept_date` | `quote` | `url` |

## 5. 질의응답 시나리오

**아직 실행하지 않았다.** 아래는 기대 동작이며, 구현 후 실제 질문·답변·근거로 바꾼다.

| # | 질문 유형 | 예시 질문 | 기대 동작 |
|---|---|---|---|
| Q1 | 대표 시나리오 — 정책 이후 수주 | "생물보안법 논의 이후 삼성바이오로직스가 공시한 수주 계약은?" | 기간 필터 + 수주 공시 검색 → 계약별 상대방·금액·기간과 근거 공시. 공시에 정책과의 관계가 적혀 있지 않으면 "인과는 공시로 확인되지 않음"을 덧붙인다 |
| Q2 | 단일 사실 | "에스티팜의 최근 단일판매·공급계약 금액은?" | 수주 공시 1건 인용 |
| Q3 | 증설 | "SK바이오사이언스의 신규 시설 투자 내용은?" | 증설 공시 인용 |
| Q4 | 정정 반영 | "○○ 계약의 계약 기간이 변경된 적 있나?" | 정정 공시를 우선 인용 |
| Q5 | 범위 밖 기업 → 거절 | "론자의 2025년 수주 실적은?" | 검색 전 거절 |
| Q6 | 근거 없음 → 거절 | "바이넥스가 미국 공장을 인수했나?" (해당 공시가 없다고 가정) | 검색 후 또는 생성 후 거절 |
| Q7 | 판단 요구 | "삼성바이오로직스 주식을 사야 하나?" | 판단 거절, 공시 사실만 안내 |

## 6. 평가 계획

결과는 [AI_EVALUATION](AI_EVALUATION.md) "공시 RAG 답변" 항목(현재 작성 전)에 기록한다.

| 대상 | 방법 | 지표 |
|---|---|---|
| M1 매칭 | 연결 50쌍을 표본으로 사람이 "같은 사건 / 관련 / 무관" 판정 | 직접 창 정밀도, 후속 창 관련 비율 |
| M1 시점 창 | 수주 공시 98건의 ±N일 기사 존재 비율 (3-2절) | N별 포착률 |
| M2 검색 | 질문 20개에 정답 공시(`rcept_no`)를 미리 지정 | 상위 5개 안에 정답 공시가 있는 비율 |
| M2 답변 | 같은 질문 20개 (답 있음 14, 거절해야 함 6) | 근거 일치율, 거절 정확도, 환각 건수 |

질문 세트는 수주·증설·M&A·실적·정정·범위 밖·근거 없음을 고루 넣어 `data/eval/rag_questions.csv` 로 저장한다 (제안).

## 8. 한계

- **5개사 공시만 있다.** 해외 CDMO나 정책 기사처럼 5개사가 언급되지 않은 기사는 공시와 연결되지 않는다. 뉴스 9,216건 중 기업 매핑이 있는 기사만 M1 대상이다.
- **시점이 가깝다고 인과는 아니다.** 후속 창 연결은 "이후에 이런 공시가 있었다"는 선후 관계만 보여준다.
- **CDMO 키워드는 규칙 기반 분류이고 정확도를 검수하지 않았다** (`docs/news_sort.md` 5절). 주제 대응의 정확도는 여기에 묶인다.
- **`event_class` 는 보고서명 정규식 분류다** (`analysis/disclosure_weights.py`). `임상·허가·기술계약` 은 "투자판단관련주요경영사항" 전체를 받으므로 내용이 섞여 있다.
- **공시는 의무 공시 범위만 담는다.** 공시 기준 금액에 못 미치는 계약이나 상대방 비공개 계약은 원문에 내용이 없어, 뉴스에는 있지만 RAG는 거절하는 경우가 생긴다.
- **표가 청크 경계에서 나뉘면** 열 이름이 빠져 숫자의 의미를 잃을 수 있다 (4-2절).
- **원문 없는 공시 3건**은 RAG로 답할 수 없다.
- **`data/db/` 와 `chroma_db/` 는 git에 없다.** 팀원마다 DB와 색인을 직접 만들거나 전달받아야 하고, 빌드 시점이 다르면 결과가 달라질 수 있다.
